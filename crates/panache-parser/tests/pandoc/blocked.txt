# Phase 7e note — Matched-pair block tags with same-line inter-tag text
# (`<p>foo</p> bar <p>baz</p>`, formerly blocked 472) was FIXED via
# option (b): `same_line_trailing_forces_opaque` in `html_blocks.rs`
# suppresses the same-line strict-block lift when the after-close
# trailing holds inter-tag TEXT before another matched-pair tag, keeping
# the line opaque for `split_html_block_by_tags`. See allowlist 472/475/
# 476/477. Same-line `<div>` inter-tag text is FIXED (Phase B,
# `graft_same_line_div_peel`): both the whitespace form `<div>x</div> y
# <div>z</div>` (corpus 0479) and the no-ws form
# `<div>foo</div>bar<div>baz</div>` (corpus 0480) now project
# `Div`/`Plain`/`Div`. Remaining divergent `<div>`-family variants
# (verified 2026-07-08, not in corpus):
#   (1) multi-line SECOND div: `<div>a</div> y <div>\nz\n</div>` -> pandoc
#       `Div`/`Plain`/`Div`; the content-scan depth model treats the
#       `</div> ... <div>` close line as depth-neutral (close then re-open)
#       so the whole span stays ONE div. Needs the depth-model rework.
#   (2) paragraph-leads-div: `foo <div>bar</div> baz` -> pandoc
#       `Plain[foo]`/`Div[bar]`/`Para[baz]`; panache keeps one `Para` with
#       RawInline tags (the general inline-parser boundary the 0472 note
#       feared).
# Both want a parser structural lift, not projector byte-walking; each is a
# full-phase effort. Deferred.
#
# FIXED 2026-07-02 (Phase A, corpus 0478): fenced-div reopened inside html
# div `<div>\n:::x\n</div>` -> pandoc `Div[Div(x)[RawBlock "</div>"]]`. The
# body-scan loop now tracks fenced-div nesting (`body_fence_depth`) and
# suspends the `</div>` close match while a fence is open, so the `</div>`
# lifts into the fence body via the implicit-close path.

# FIXED 2026-08-07 (corpus 508): the general pandoc blockquote-laziness
# rule. `handle_blockquote_line` now gobbles every non-blank lazy line back
# into the open quote with its indentation dropped, instead of only holding
# the quote open for an open Paragraph/ListItem/DefinitionList. The
# terminators are pandoc's own `endline` guards, anchored at byte 0 of the
# raw line (`Parser::blockquote_gobble_ends_at`).

# FIXED 2026-08-07 (corpus 509): line-block continuation now beats the
# marker. `parse_line_block` tests `continues_previous_line` before
# `parse_line_block_line_marker`, matching pandoc's `lineBlockLine`, which
# runs `many (try (char ' ' >> anyLine))` inside the line it just read.
# An indented marker line therefore folds into the line above
# (`| a\n  | b` -> `[[a, |, b]]`). The blockquote-laziness guard keeps
# `> | a\n  | b` at two lines, since the quote reader drops the lazy
# line's indent before `lineBlockLine` ever sees it.

# FIXED 2026-08-07 (corpus 512): the projector no longer rebuilds a code
# block's payload from `CODE_CONTENT`'s raw text, which used to put every
# container-prefix token the emitter peeled off back into the `CodeBlock`
# string. `pandoc_ast::code_content_text` walks the tokens instead.
#
# The recorded ambiguity — a line-leading `WHITESPACE` inside `CODE_CONTENT`
# is a container prefix for a fenced block but the significant indent of an
# indented one — resolves from the emitters, but the split is NOT
# fenced-vs-indented:
#
#   - `BLOCK_QUOTE_MARKER` and the one space it owns are always prefix.
#   - Remaining line-start whitespace is dropped token-wise only for a fenced
#     block directly inside a blockquote (`fenced_in_blockquote`), where the
#     emitter's consumption is exactly pandoc's: marker padding, or the
#     lazy-line gobble.
#   - Everywhere else the host indent comes off by COLUMN
#     (`strip_leading_spaces_per_line`), because the emitter's token boundary
#     is not column-exact once tabs are involved: for a `:\t` definition
#     marker (content column 4) it peels `"\t\t"` — 8 columns — into the
#     prefix token, and dropping that whole token loses 4 columns of code.
#     Corpus 44 is the guard; it regressed on the first (token-only) attempt.
#
# Tabs are expanded against the raw line column, before the prefix comes off,
# mirroring pandoc's `tabFilter`: `> \tcode` is `"  code"`, not `"    code"`.
# See 0515-0519 for the shapes this pinned.

# 513 - blocked on a PARSER gap in the fold's *entry* condition, distinct from
# the body-line gobble above. `> - a`/`   ```` ``` ````/`   c`/`   ```` ``` ````
# never reaches `fold_lazy_line_into_blockquote`: the lazy-list-continuation
# gate in `handle_blockquote_line` runs first and hands the line to the open
# list item, which buffers it as PLAIN text (the fence degrades to an
# `INLINE_CODE` span). Pandoc drops the indent instead, so the fence opens at
# column 0 and lands as a sibling of the list inside the quote. Unblocking means
# ordering that gate against `blockquote_gobble_ends_at`, which governs every
# `> - a`/`  b` shape - too wide to fold into the body-line fix.
#
# This shape also fails `panache debug format --checks idempotency` (the second
# pass re-quotes the buffered lines as `>   >   c`), byte-identically before and
# after the body-line gobble landed. Worth fixing ahead of the conformance
# delta.
